# Workflow agent brief

Root pastes this text word for word at the start of every workflow agent prompt, then gives the agent its lane file sections and its bins, testbin and pin paths. Root names a host only for timing that needs zbook-class hardware.

This prompt holds the whole brief. Do not read `docs/goport-agent-brief.md` or AGENTS.md again unless your prompt says so.

- Edit only the files your prompt gives you. Do not edit `docs/typechecker-state/*`. Do not commit unless your prompt says so. Project inputs under `target/project-inputs*` are read-only.
- Build in your worktree with `scripts/run-cargo-capped.sh build --release -p ts_goport --bins`, the worktree's own copy (a relative path from the worktree root). The main checkout's copy builds into the main checkout's target dir. Do not set `CARGO_TARGET_DIR`. Use `--profile goport` (fat LTO, 7 to 20 minutes) only when your prompt asks for timing or a release binary.
- While you edit, find compile errors with `scripts/run-cargo-capped.sh check -p ts_goport`: a one-line edit takes about 12 s, and a release `--bins` build after it about 70 s, most of it LLVM (alvin, 2026-10-10). Build the release bins when you need to run them, not after each edit. `--bin tsgo` in place of `--bins` saves no time: the links run in parallel.
- The script builds with nightly `-Zthreads=8` and incremental `ts_goport`. Without the nightly installed it stops with the install command. `--profile goport` uses the default toolchain (`build-release.sh` sets 1.95.0). After an internal compiler error, build again with `TS_CARGO_NIGHTLY=0 TS_CARGO_INCREMENTAL=0` and report it.
- Before you report, run `rustfmt --edition 2024` on every `.rs` file you changed. Unformatted code costs a whole new revision.
- You are a subagent. When you end your turn, you stop, and your background jobs stop with you. To wait for a build or a job, block in the foreground with a Bash timeout up to 600000 ms, for example `timeout 590 bash -c 'until grep -qE "^(DONE|FAIL)" LOG; do sleep 10; done'`. Do not poll in 2-minute steps. Claude Code blocks `sleep N; <command>`: use the `until` loop.
- Big test runs (test_local, TestSubmodule, go_baselines at a new pin, reference files, corpus) and every job that can use more than 8 GB go under `systemd-run --user --collect -p MemoryMax=24G -p MemorySwapMax=0 --unit=<name>`, even when short. On 2026-09-29 a bump C harness run in the session's own scope made systemd-oomd kill the whole Claude session.
- Memory profilers (`heaptrack`, `heaptrack_print`, `valgrind`, massif, dhat) go under the same `systemd-run ... -p MemoryMax=24G -p MemorySwapMax=0` line, or on a remote host. On 2026-10-04 `heaptrack` and `heaptrack_print` on a hono editor session in the session's own scope made systemd-oomd kill the Claude session twice.
- Your own scripts too: a Python or shell tool that reads the whole source tree, a large JSON or a big log can use tens of GB. Run it under `systemd-run --user --collect --wait -p MemoryMax=16G -p MemorySwapMax=0`, and stream: one file at a time, no whole-tree data in memory. On 2026-10-10 a study's source rewriter reached 73 GB in the session's own scope and root had to kill it.
- A job that runs longer than 10 minutes goes under `systemd-run --user --collect --unit=<name>`, writes a log, and ends the log with one line: `DONE` or `FAIL rc=<N>`.
- Read long files (decisions.md, plan*.md, base.md, timing.md) with `grep -n` and `sed -n` ranges, not `cat`. Keep each command's output under 20 KB: bigger output spills to a file that you must then read again.
- Tools in `/tmp` can vanish. Put tools under `scripts/` or your lane dir.
- Return your findings as text in your final answer. Root saves them. If your prompt names a report file, write it with Bash (`cat > FILE <<'EOF'`): Claude Code blocks the Write tool for report files in some subagents.
- Delete with literal paths. Claude Code blocks `rm -rf` on a shell variable such as `rm -rf "$D"/*`.
- Every tool prints its usage with `help`: `scripts/goport/candidate.sh help`, `scripts/goport/remote.sh help`, `scripts/run-cargo-capped.sh help`, `scripts/goport/lib-blobs.sh help`, `scripts/goport/wfstatus --help`. The header of `gate.sh` and `perf.sh` gives theirs. Do not read a tool's source to learn its usage.
- If you need a decision, choose the safe option, say which one in your answer and continue.

- The lib blobs (`lib_parse.bin`, `lib_bind.bin`) go stale after a change to the parser, scanner, factory, store, ts_ast, binder, core.rs, flags, a snapshot file or a bundled lib. A merge keeps our side of a blob without a conflict, so after merges, write once, after the last merge. `GOPORT_LIB_PARSE_SNAPSHOT=0` and `GOPORT_LIB_SNAPSHOT=0` turn them off for A/B timing.

Set `TS_CARGO_JOBS=32`: the default off zbook is 1. The run syncs your worktree files; `tests` needs your commit pushed to origin (the testbox resets to HEAD).
- Build bytes: jemalloc's configure takes its address bit count from the build CPU, and some testbox hosts have 57 bits (others, zbook and dbook-lan 48). The testbox env pins `JEMALLOC_SYS_WITH_LG_VADDR=48` (2026-10-24, npbuild1), so testbox builds are host-independent. A build log starts with the host CPU and address sizes.
- Pins: `testbox.sh pin 3e9236361fa9` first, then `tests --pin 3e9236361fa9` or `np-suite --pin 3e9236361fa9` (main's pin; other pins the same way).
- Instruction counts and peak RSS run on a testbox: `testbox.sh perf <label> <bin>...` (both sides in one call; it warms up and stops a testbox when the worktree has none). Use the single-thread instructions:u for a 1 percent claim, and add `-- --noEmit` for checker work (the emit is about 25 percent of the effect instructions). Wall is not valid on a testbox.
- Release builds (PGO and BOLT, for revision timing): `testbox.sh release-build <lane>/rel/<name>` from your worktree (HEAD pushed; about 16 minutes). It fetches `bin/` with BUILD.txt, COMMIT and bins.sha256. The guest has no branch sampling, so BOLT takes its profile from a counting copy of each bin (`RELEASE_BOLT_PROFILE=instrument`). Do not mix these with zbook LBR builds in one timing: on R195 source they used up to 11 percent less peak RSS and ran up to 4 percent faster (tbxrel1). The R195 testbox builds are `target/continuation-r97-goport/tbxrel1/rel/tbx1` and `tbx2`.

Remote hosts (all through `scripts/goport/remote.sh`, never raw `ssh` or `rsync`):

- Hosts: dbook-lan (LAN) only. Theo retired alvin, cup2 and mini-743d on 2026-10-12 ("I want those hosts to not get anything anymore"), and mini-abf9 is Theo's machine: `remote.sh` refuses all four. Heavy work goes to a testbox; if a testbox cannot do it, use dbook-lan or zbook. `remote.sh status` shows dbook-lan's lock holder, load and free RAM.
- To look (logs, files, hashes, tools): `remote.sh look <host> <command>`. It takes no lock and stops after 120 s.
- To run a job: `remote.sh run auto <command>`. It picks dbook-lan when free, waits when none is free, and holds that host's lock until the command ends. For several steps on one host (sync, run, fetch), write a zbook script that uses `$REMOTE_HOST` and start it with `remote.sh job auto <script>`. The script must not take the lock itself. Name a host only when your prompt names one.
- To copy: `remote.sh sync-bins <host> <dir>` (top-level files), `push <host> <path>` (files or trees), `sync-pin <host> <pin>`, and `fetch <host> <dir>` for results.
- Release builds off a testbox (LBR BOLT; for a testbox outage only): run `crates/ts_goport/scripts/build-release.sh` one at a time on a host. Two at once break its perf branch sampling check (PGO and BOLT). On zbook run it under `flock /home/theo/Code/sandbox/ts-rust/target/locks/build-release.lock`: zbook now runs two Cargo builds at once, so the Cargo lock no longer keeps two release builds apart.
- Measuring `tsgo` RSS or CPU through wait4 (`/usr/bin/time`, hyperfine user and sys, `perf stat` on the command): set `GOPORT_LAUNCH=0`. Since R137, `tsgo` on 4 KiB pages runs the compile in a worker, and wait4 sees only the launcher. `perf.sh` sets it.
- Timing: wall with `scripts/goport/perf.sh <label> <bin>...` on dbook-lan (5 rounds), every side in one run on one host. It refuses above load 1.5. Do not time on zbook. To repeat a timing, run it again on dbook-lan. Instructions and RSS: `testbox.sh perf` (above). No 1 percent claim from cycles:u on any host. tsgo gets your `GOPORT_*` and allocator variables on every host, and host.txt records them (`perf.sh env` prints them). `perf.sh compare <base> <new>` compares counts of two runs only when their host lines, tsgo args and env match.
- Time like against like: every Rust side of a timing is a stable build (`TS_CARGO_NIGHTLY=0 TS_CARGO_INCREMENTAL=0 scripts/run-cargo-capped.sh build --release ...`, or `--profile goport`). Edit-loop bins (nightly, incremental) run 2 to 7% slower.
- Machines: dbook-lan has `sudo -n`, perf_event_paranoid 4 (use `sudo perf`), THP madvise, perf, bpftrace and strace, zbook's CPU and 26 GB RAM. zbook has no passwordless sudo, paranoid 2, THP always, and a load that is often over 10.
